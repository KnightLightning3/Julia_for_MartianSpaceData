# Julia 科研函数库——架构重构团队总纲 V2

## 1. 项目背景

本项目是一个长期用于个人科研工作的 Julia 函数库，主要服务于 MAVEN / Mars ionosphere / space plasma 等科研数据处理、计算和分析任务。

该项目并非从一开始按照严格的软件工程规范设计，而是在实际科研使用过程中“随用随加”逐渐形成。因此：

- 项目中已经积累了较多功能；
- 不同阶段加入的代码可能存在功能重叠；
- 部分功能的模块归属可能并不理想；
- 部分模块之间可能存在历史遗留的依赖关系；
- 同一类功能可能散落在不同文件或模块中；
- 随着功能不断增加，原有结构可能逐渐失去清晰的边界。

本轮工作的目标不是重新开发整个项目，也不是立即进行函数级性能优化。

本轮工作的核心是：

> **从整体架构层面重新理解 Julia 部分，将已有功能进行合理的迁移、合并、整理和重新归类，同时建立一套能够支持未来持续增加功能的架构规范。**

最终希望得到一个：

> **结构清晰、功能组织合理、依赖关系明确、容易迁移、容易验证，并且能够持续自然扩展的 Julia 科研/数据处理函数库。**

# 3. 本轮最重要的目标

本轮不是简单地“把代码重新分文件”。

真正需要解决的是：

## 3.1 功能应该属于哪里？

例如：

```text
某个函数现在位于 Module A

但它实际属于：
    Coordinate
    Geometry
    DataIO
    Physics
    Math
中的哪一个？
```

需要从功能语义和依赖关系判断，而不是单纯根据当前文件位置决定。

---

## 3.2 哪些功能应该合并？

如果多个模块实际上承担高度重叠的职责，需要考虑：

```text
Module A
Module B
Module C
     ↓
统一的合理 Module
```

但禁止为了减少文件数量而机械合并。

---

## 3.3 哪些功能应该拆分？

如果一个模块承担过多不同职责：

```text
Module A
 ├── Data I/O
 ├── Coordinate conversion
 ├── Physics calculation
 ├── Plot preparation
 └── Misc utilities
```

需要考虑合理拆分。

---

## 3.4 模块之间应该如何依赖？

希望逐渐形成明确的依赖方向。

例如：

```text
基础工具
   ↓
数学/数据结构
   ↓
领域基础功能
   ↓
具体科研计算
   ↓
高层分析功能
```

避免形成：

```text
A → B
↑   ↓
D ← C
```

这种难以维护的循环依赖。

---

# 4. 最重要的新要求：建立“未来功能添加规范”

这是本轮架构工作的核心成果之一。

项目过去具有：

> “需要什么就添加什么。”

这种模式在科研工作早期非常有效，因此不应该简单否定。

真正需要解决的是：

> **继续允许快速添加功能，但必须让新增功能能够自然进入既有架构。**

因此最终必须形成明确规则，例如：

```text
如果新增的是数据读取功能
    → 应该进入哪里？

如果新增的是坐标变换
    → 应该进入哪里？

如果新增的是数学工具
    → 应该进入哪里？

如果新增的是 Mars ionosphere 专用计算
    → 应该进入哪里？

如果一个新函数同时依赖两个已有模块
    → 应该如何处理？

什么时候应该新建 Module？
什么时候应该加入已有 Module？
什么时候应该拆分 Module？
什么时候应该建立新的子层？
```

最终应该形成一套**低摩擦的 Feature Addition Convention**。

原则是：

> 新功能可以快速增加，但不能继续无规则地增加。

# 7. 建议的阶段结构

具体编号可由队长根据已有 P5/P6 状态调整，但逻辑上至少应包含以下阶段。

- 当前代码；
- 上一轮日志；
- 已完成的 MD；
- 修改记录。

重点不是重新研究整个项目，而是回答：

```text

上一轮完成了什么？

哪些旧结论可以继承？
哪些地方需要重新确认？
```

---

## Phase B：Functional Architecture

建立：

```text
Function
→ Capability
→ Module
→ Dependency
```

层次结构。

重点是理解：

> 项目“实际上提供了哪些功能”。

而不是简单统计 `.jl` 文件。

---

## Phase C：Target Architecture

设计目标架构，包括：

- Module 划分；
- 文件组织；
- 功能归属；
- 依赖方向；
- public API；
- namespace；
- extension points；
- 新功能加入规则。

目标架构必须考虑：

> 当前项目 + 未来持续增加科研功能。

不能只为当前代码“整理得漂亮”，而忽略未来扩展。

---

## Phase D：Migration Plan

将架构调整转化为明确任务。

建议使用：

```text
MOVE
MERGE
SPLIT
RENAME
DEPRECATE
CREATE
```

等操作类型。

每个迁移任务应具有唯一 ID，例如：

```text
MIG-001
MIG-002
MIG-003
...
```

并明确：

- 原位置；
- 目标位置；
- 涉及文件；
- 影响 API；
- 依赖影响；
- 是否可以并行；
- 验证要求。

# 8. AST 验证必须提前建立

这是本轮非常重要的原则。

**不要等重构完成以后才考虑如何验证。**

应该：

```text
Migration Plan
      ↓
AST / Validation Framework
      ↓
确认验证框架本身可运行
      ↓
开始大规模迁移
```

AST 系统至少应能够辅助完成：

- function definition 提取；
- module 提取；
- `using` / `import` 分析；
- `export` 分析；
- function call 提取；
- 跨模块调用分析；
- API 影响分析；
- 重构前后结构对比。

# 9. Function Call Table

最终需要建立一个可以由程序自动执行的函数调用表。

不要让 AI：

```text
手工调用函数
→ 看结果
→ 再手工调用另一个函数
→ 比较结果
```

而应该形成：

```text
Call Table
     ↓
Validation Script
     ↓
自动执行
     ↓
Old Result
     ↓
New Result
     ↓
自动比较
```

例如可以设计成 TOML / JSON / Julia 数据结构。

每一个 case 可以记录：

```text
case_id
module
function
arguments
expected_behavior
comparison_method
tolerance
tags
```

---

# 10. 验证的核心原则

验证重点是：

> **重构前后的计算行为是否一致。**

需要考虑：

- 标量；
- Array；
- Tuple；
- NamedTuple；
- Struct；
- DataFrame；
- `NaN`；
- `Inf`；
- `missing`；
- 数值误差；
- Absolute tolerance；
- Relative tolerance。

不能简单使用：

```text
old == new
```

作为所有科学计算的统一标准。

也不能为了让测试通过而随意放宽 tolerance。

如果结果不一致，需要判断：

```text
真正的架构迁移导致行为改变？
数值误差？
原代码 bug？
新代码 bug？
测试数据问题？
```

# 12. DeepSeek Pro —— Principal Architecture / Scientific Reviewer

DeepSeek Pro 保留原有定位：

> **高级架构 + 科研计算专家；同时承担需要复杂推理的代码实施。**

主要负责：

# 15. DeepSeek 双渠道与多实例调度

DeepSeek Pro / Flash 的职责由模型能力和任务性质决定，不由渠道名称决定。两种渠道应明确标注：

| 渠道 | 已知特点 | 调度定位 |
| --- | --- | --- |
| DeepSeek Official | 官方渠道；实际可用模型、费用与并发额度以配置为准 | 承担主要编码、关键路径迁移、及时反馈及验证任务；按互不重叠的范围多开 |
| 中科大公共平台 | 按用户说明免费，但速度较慢 | 穿插一个并行编码/自动化实例，承担低耦合、非关键路径、允许较长响应时间的任务 |

初始实例安排（正式执行前依据实际可用路由、范围与配额确认）：

- `captain`：GPT-6.1-SOL，仅协调与文档；
- `chief-architect`：Claude Opus 5.5，仅架构设计与审定；
- `pro-architecture-official`：DeepSeek Pro / Official，高级架构专家，负责模块边界、依赖方向、API 与扩展性独立审查；
- `pro-science-official`：DeepSeek Pro / Official，科研计算专家，负责科学语义、数据契约、单位/坐标约定及行为兼容性独立审查；两者分工互补，不重复完整扫描；
- `pro-code-official-1..N`：DeepSeek Pro / Official，按需多开，负责复杂代码实现；
- `flash-code-official-1..N`：DeepSeek Flash / Official，按需多开，负责主要迁移和常规代码实现；
- `flash-validation-official-1..N`：DeepSeek Flash / Official，按需多开，负责 AST、调用表、回归及自动化代码；
- `deepseek-code-ustc-1`：中科大公共平台的一个 DeepSeek 实例，选择该平台实际可用的 Pro 或 Flash，承担独立迁移单元或非阻塞自动化代码任务，不假定其支持全部型号。

调度规则：

1. 先确定真实模型 ID、渠道与连通性，再注册对应实例；未确认的路由不得编造。
2. 官方渠道承担关键路径；中科大公共平台实例用于补充并行产能，不使整个阶段等待慢渠道。
3. 多开数量随可并行的迁移单元、上下文成本和平台额度调整，不为了多开而重复扫描或重复实现。
4. 每个任务明确 Task ID、输入证据、允许修改路径、禁止修改路径、依赖和验收要求；不同实例的写入范围必须互斥。
5. 编码与验证修改同一范围时必须串行安排；实现者与独立审查者分离。
6. 慢渠道超时或需转交时，先撤销旧任务所有权并确认旧实例停止写入，再转交官方实例，禁止两个实例同时修改同一范围。
7. 用户已授权依照计划开始工作：先继承已有工作并开展架构分析；目标架构与迁移计划完成后提交人工审查，再依据审定架构安排代码迁移，不提前自由重构。
8. **算上 GPT-6.1-SOL 队长，同时最多 8 个 Agent（队员最多 7 个）**。架构阶段安排总架构师、两名分工明确的 DeepSeek Pro、官方 Flash 状态恢复实例和一个中科大 Flash 补充实例，共 6 个 Agent 含队长；其余 2 个名额留待架构明确后按互斥代码范围使用。不得由队员自行创建子 Agent；新增、替换与任务转交由队长统一计数调度。
9. **采用汇报驱动调度，不反复查询其他 Agent 工作进度**。成员在交付、阻塞或需要决策时主动汇报；队长收到汇报后再处理状态、依赖与下一阶段，等待期间不轮询、不催促。

# 16. 高价模型的使用原则

高价模型不是用来替代低成本模型做所有事情。GPT-6.1-SOL 与 Claude Opus 5.5 均不承担具体代码工作。

本团队采用：

```text
GPT-6.1-SOL：任务队长（协调、调度、证据与交付；不编码）
│
├── Claude Opus 5.5：总架构师（架构设计与审定；不编码）
│      └── DeepSeek Pro：高级架构 / 科研语义独立审查
│
└── DeepSeek 主要代码队伍（可多开，严格隔离写入范围）
       ├── Official / Pro：复杂实现与科学语义敏感修改
       ├── Official / Flash：大量迁移与常规实现
       ├── Official / Flash：AST、调用表、回归与自动化
       └── 中科大公共平台 / DeepSeek：一个免费慢速补充实例
              └── 非关键路径的独立代码 / 自动化任务
```

通过精选输入证据、按需架构会审与明确任务合同控制成本；只有遇到明确困难时才升级编码模型，不把实现工作转交队长或总架构师。

# 17. 最终决策权

AI 团队不拥有科研意义上的最终裁决权。

最终仍由项目使用者判断：

- 科研意义；
- 物理意义；
- 数据处理逻辑；
- API 使用习惯；
- 哪些抽象符合实际科研工作；
- 哪些架构虽然“软件工程上漂亮”，但不适合实际科研使用。

特别注意：

> **AST regression 只能证明重构前后行为一致，不能证明原始行为在科学意义上一定正确。**

因此：

```text
AI：
保证架构合理
保证迁移完整
保证行为一致
保证可扩展

用户：
最终确认科研正确性
```

# 18. 最终希望形成的项目状态

本轮结束后，希望形成如下状态：

```text
                         Julia Library
                              │
             ┌────────────────┼────────────────┐
             │                │                │
          基础层            领域层            高层功能
             │                │                │
        Math / Data       Physics / Coord    Analysis
             │                │                │

                              │

                              │
                       User / Research
```

实际模块名称不预设，由架构分析决定。

但必须满足：

### 清晰

每个模块有明确职责。

### 低耦合

模块之间尽可能通过清晰接口通信。

### 可扩展

增加新功能时有明确归属。

### 可迁移

未来发现架构仍需调整时，不需要大规模推倒重来。

### 可验证

重要功能能够通过自动化调用表进行 regression。

### 适合科研

不能为了追求纯软件工程形式而牺牲科研使用效率。

# 19. 核心原则总结

本轮工作始终遵守以下原则：

1. **先理解，再重构。**
2. **先架构，再编码。**
3. **先建立验证能力，再大规模迁移。**
4. **优先解决功能组织，而不是函数内部优化。**
5. **不为了减少文件数量而机械合并模块。**
6. **不为了“看起来漂亮”而破坏科研使用习惯。**
7. **充分继承上一轮 AI 已经完成的工作。**
8. **能自动化的验证绝不依赖 AI 手工执行。**
9. **允许多 Agent 并行，但必须严格隔离文件所有权。**
10. **GPT-6.1-SOL 为任务队长，负责全局协调，不负责具体代码。**
11. **Claude Opus 5.5 为总架构师，负责架构设计与审定，不负责具体代码。**
12. **DeepSeek Pro 保留高级架构与科研语义独立审查定位，并由分离的编码实例承担复杂实现。**
13. **DeepSeek Flash 保留主要代码实施及低成本自动化、AST、调用表和验证定位。**
14. **DeepSeek Pro / Flash 可多开；Official 承担主要及关键路径工作，穿插一个中科大公共平台免费慢速实例承担非关键路径代码任务。**
15. **不同编码实例严格隔离写入范围，实现与独立审查分离；最终科研正确性由项目使用者确认。**

最终目标不是得到一个“最漂亮”的软件工程项目，而是得到一个：

> **能够长期服务科研工作，并且随着科研需求不断增加而仍然能够自然生长的 Julia 函数库。**
